Challenges that people with disabilities may have using voice interfaces:


Voice-based technologies like Siri, Amazon Echo, and Google Home create significant accessibility barriers for people with both apparent and less apparent disabilities. For instance, speech differences like stuttering or vocal impairments can make common or default wake phrases like "Hey Siri" or "OK Google" difficult for users to pronounce. Also, hearing and auditory processing differences can make audio-only feedback from a voice assistant difficult to use because users cannot visually verify whether the assistant heard them correctly, or they heard the assistant correctly. Furthermore, having a single, fixed wake phrase and short time windows for users to speak before the AI responds can create difficulties and stress for people with memory differences or social anxiety, since it assumes a standard user who speaks quickly and clearly on the first try.

Existing Solutions Which Address This Issue:


Many voice-based technologies currently have several solutions to help improve accessibility of their products. For example, nearly all smart speakers have physical buttons for muting or triggering actions. In addition, devices like the Alexa Echo Show utilize a screen display to display captions and visual text to users, although it is not the sole use for it. Also, Google Home and Alexa offer multiple language input/output options and voice profiles that they are able to save, to detect which user is speaking. However, these features still have some limitations. Physical buttons require the user to be near the physical device and also require use of hands. Language options still require speech to conform to patterns that the AI can recognize and requires speech. Furthermore, while voice-based technologies with screens are useful for showing responses or captions of your input, I have found that many of them do not allow users to have a chance to review and fix misheard text before the assistant executes an action, as this typically only happens with text-based technologies, where the user can click to edit their input.

Potential Solutions & My Prototype

To address these challenges, I came up with two potential solutions, which were actually combined into a single functional prototype that I created using Claude Code for the development. The first solution is letting the user choose their own primary and backup wake command, which can be anything of their choosing, such as “Banana”. This does not even need to be a spoken word or phrase as the user would also be able to input a series of screen taps, or claps and use that as their wake command. This gets verified and created through a setup flow that plays back the input and requires the user to repeat it to ensure the assistant understood the user correctly.

The second solution is having visible patience for the user through having a 10 second timer after the user stops speaking, to give them time to continue if needed (it will pause again if the user continues talking). It also gives the user confirmation that it heard the user correctly. The idea is that before executing any request, my prototype reads back what it heard and asks "Is that correct?", giving the user total control to confirm or re-speak before an action happens. If the user remains silent, my assistant will respond with "No rush, wake me up when you are ready" and go to “sleep”, which removes the pressure of running out of time to speak, as well as give a clear visual state on the screen to aid as well.

In my prototype, both of these solutions are put together into the voice assistant interface. My working prototype mainly guides users through the set up flow of the wake commands, but also allows users to test out waking up the assistant, inputting a general command through voice, and having the assistant read it back and show it to the user.
